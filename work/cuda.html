Parallel image processing in CUDA

01 · Try it

What a Sobel filter does

02 · The problem

A 3×3 stencil is perfectly parallel

Both filters compute each output pixel from its 3×3 neighbourhood. No output pixel depends on another output pixel, so the work splits cleanly. A CPU loop walks through all 1,048,576 pixels of a 1024² frame one after another. A GPU can hand each pixel to its own thread.

Sobel convolves the neighbourhood with two kernels, Gx for horizontal change and Gy for vertical change, and keeps the gradient magnitude √(Gx² + Gy²), clamped to 255. The Gaussian blur uses the 1-2-1 weighted kernel divided by 16.

03 · Approach

One thread per pixel, 16×16 blocks

Threads are grouped into 16×16 blocks (256 threads each). The grid is sized with a ceiling division, ((w + 15) / 16, (h + 15) / 16), so any image size is covered. Each thread computes its row and column from its block and thread index, skips the one-pixel border, and writes a single output byte.

At 1024² that is a 64×64 grid of blocks: 4,096 blocks and about a million threads.

Each square is one 16×16 thread block. Highlighted: four blocks, 1,024 pixels. 
__global__ void processSobelGPU(unsigned char* d_in, unsigned char* d_out, int width, int height) {
    int c = blockIdx.x * blockDim.x + threadIdx.x;
    int r = blockIdx.y * blockDim.y + threadIdx.y;
    int Gx[3][3] = {{-1, 0, 1}, {-2, 0, 2}, {-1, 0, 1}};
    int Gy[3][3] = {{-1, -2, -1}, {0, 0, 0}, {1, 2, 1}};
    if (r > 0 && r < height - 1 && c > 0 && c < width - 1) {
        float sumX = 0.0f, sumY = 0.0f;
        for (int i = -1; i <= 1; i++)
            for (int j = -1; j <= 1; j++) {
                int pixel = d_in[(r + i) * width + (c + j)];
                sumX += pixel * Gx[i+1][j+1];
                sumY += pixel * Gy[i+1][j+1];
            }
        int mag = (int)sqrtf(sumX * sumX + sumY * sumY);
        d_out[r * width + c] = (unsigned char)(mag > 255 ? 255 : mag);
    } else if (r < height && c < width) d_out[r * width + c] = 0;   // zero the border
}

From benchmarks/benchmark.cu. The CPU reference in the same file runs the identical arithmetic in a nested loop.

05 · Reading the numbers honestly

What this benchmark does and doesn't show

  • Kernel time only. The GPU figure covers the kernel, not the cudaMemcpy transfers to and from the device. End-to-end speedup for a single frame would be lower; it matters most when many frames are processed while data stays on the GPU.
  • Synthetic input. The test image is a repeating 0–255 gradient, which is fine for timing because the arithmetic is the same for every pixel.
  • The speedup fell at 4096². At 16.7 million pixels the gain dropped from 135.6× to 65×. Finding out why is the first thing I'd profile.
06 · Next

What I'd do next

Tile into shared memory

Each pixel is read by nine threads from global memory. Loading an 18×18 tile (block plus a one-pixel halo) into shared memory once per block should cut those reads sharply.

Put weights in constant memory

Move Gx, Gy and the Gaussian weights into __constant__ memory so they are broadcast instead of rebuilt in every thread.

Time the whole pipeline

Report transfer plus kernel time, try pinned host memory, and overlap copies with compute using streams.

Real images and fused filters

Load real photos, run blur then Sobel in one pass, and use a separable Gaussian (two 1D passes) for larger kernels.
